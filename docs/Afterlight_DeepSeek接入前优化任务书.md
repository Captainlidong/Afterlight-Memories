## 1. 本轮目标与范围

### 1.1 要达到的结果

完成本轮优化后，系统应满足：

1. 用户编辑、生成结果和素材状态不会因慢请求、重复点击、失败或多标签页而被静默覆盖。
2. 分析中断后可以复用仍有效的已完成结果，只补失败或过期部分。
3. AI 请求的实际并发受到限制，用户能看懂当前进度、实际请求数和剩余调用额度。
4. 模型响应在完整解析、结构检查、引用检查及用户编辑合并后才成为正式作品；异常响应不能覆盖旧成果。
5. DeepSeek 接入所需的可靠性基础准备好，后续只需配置和小样联调，不再借真实付费调用排查这些可离线复现的缺陷。

### 1.2 本轮明确不扩展

- 不新增自动放映、创作意图问卷、策展理由交互等其他功能。
- 不另建第二套 AI 应用，保留同一应用中的 Demo/AI 两种模式。
- 不新增公网部署、登录、多租户或分布式任务系统。
- 不在本轮填写真实密钥、发送真实照片或调用 DeepSeek；不要把“以后接入测试”解释为现在授权外发。
- 不重排现有页面、不大幅改视觉风格；需要增加的信息嵌入现有任务进度和 AI 状态区域。

### 1.3 已有能力应保留并复用

现有系统已有视觉、筛选、主题、叙事 adapter，以及图片预处理、schema、调用记录、预算、缓存、用户覆盖、确认门和版本机制。先核对现状，扩展这些机制，不将它们全部删除重写。

已有 `src/lib/agents/credibility.ts`、各 adapter 的引用检查和 QA 也应继续使用。本文要求补足遗漏、统一执行边界，不意味着现有系统完全没有校验。

API Key 继续只放服务端，前端只访问本项目接口；不把 Key、Authorization、图片 Base64、完整私人照片信息写到页面、日志或导出。

## 2. 模块一：保存、生成与素材状态保护

对应用户要求第 2 项。优先级最高，先保证不会丢用户内容。

### 2.1 修复旧请求覆盖新叙事

**现状入口：** `src/app/api/exhibitions/[id]/narrative/route.ts`。

现有流程在读取请求正文前取得影展和叙事，等待正文时若其他操作发布新版本，后续可能仍使用旧对象通过版本检查，并以旧叙事重建整份内容。此前已在隔离环境复现“接口返回 200，但新标题被旧标题覆盖”。

**必须实现：**

1. 先解析请求，再在短事务内读取最新影展、最新叙事和编辑覆盖层。
2. 在同一原子操作中完成：检查运行占用、比较预期修订、应用编辑、合并、校验、持久化、更新必要的失效标记。
3. 版本冲突返回可识别的 409，例如 `version_conflict`；该请求对正式叙事、编辑覆盖层、版本及失效标记均不得有部分写入。
4. 更新接口和前端对“预期修订”的约定。生成/回滚修订和手工编辑修订的含义要清楚；不能只检查生成版本，漏掉同一生成版本内的双标签页编辑覆盖。
5. 可以复用或小幅扩展现有修订字段，不要求建立复杂版本平台。若新增编辑修订字段，提供兼容现有数据的迁移。
6. 事务内不等待模型、文件处理或网络请求，不持有长事务。

**冲突时的用户体验：**

显示：“内容已在其他操作中更新，你的草稿已保留，请查看最新内容后再保存。”

不要直接清空编辑器，不自动用服务器版本替换用户正在写的草稿，也不要静默重试强行覆盖。

### 2.2 修复保存期间继续输入丢字

**现状入口：** `src/features/narrative/FieldEditor.tsx`、`useSaveBarrier.ts` 及叙事页保存调用。

现有保存会先捕获草稿 A，等待请求后再退出编辑；输入框在等待期间仍可变化为 AB，旧请求回包可能把新草稿重置为 A。

**建议采用的最小可靠方案：**

- 保存期间输入框暂时只读，保留文字并显示“正在保存”；保存和取消按钮防重复点击。
- 请求失败时解除只读、保留草稿和错误提示；成功后使用服务端确认的最新修订。
- 如果现有交互需要允许继续输入，则记录草稿修订；旧请求成功时不得覆盖较新草稿或关闭编辑器，应明确显示“当前修改尚未保存”。两种方案选择一种完整实现，不同时叠加复杂行为。
- “下一步”必须等到最新草稿保存成功。保存失败、版本冲突或仍有新草稿时留在当前阶段。
- 不因失焦、按回车和点击下一步同时发生而提交重复保存。

### 2.3 生成意图成功后再生效

**现状入口：**

- `src/app/api/exhibitions/[id]/runs/narrative/route.ts`
- `src/app/api/exhibitions/[id]/narrative/regenerate/route.ts`
- 现有编排器和生成意图机制

普通 narrative 入口存在“先改语气，再尝试启动任务”的顺序。已有任务时即使接口返回 409，语气仍可能被修改。专用 regenerate 入口已有更完整的处理，应统一语义。

**必须实现：**

1. 语气变更、是否清除未锁定编辑等生成意图跟随本次任务，正式生成成功并通过最终校验时才原子应用。
2. 启动被拒绝、请求重复、模型失败、输出不合法、任务失去所有权时，旧叙事、旧编辑、旧语气和旧正式版本不变。
3. 重复 `request_id` 返回既有任务结果，不创建新任务、不多改配置、不重复清除编辑。
4. 继续保留用户锁定和必须保留照片的语义，不能借重新生成覆盖用户明确决定。

### 2.4 上传与任务发布都要核对最新状态

**现状入口：**

- `src/app/api/exhibitions/[id]/photos/route.ts`
- `src/lib/orchestrator/orchestrator.ts`
- agent 结果落库与正式发布的位置

上传表单读取和图片处理包含异步等待；只在开始时检查一次是否运行中，不能保护最后提交。此前已隔离复现：上传通过初次检查后启动任务，上传仍返回 201 并改变素材修订。

**必须实现：**

- 图片读取和预处理可在事务外完成；最后提交时，在短事务内重新检查影展存在、任务占用、数量上限和相关素材修订。
- 若状态已不允许上传，返回清晰错误，清理仅属于本次请求的暂存文件，不清理其他请求或已有素材。
- 编排器与 agent 发布结果时统一检查任务状态、租约/所有权、冻结的输入修订；检查与持久化不能再留下新的竞争空窗。
- 不仅检查“任务还属于我”，还要检查“这些结果仍对应当前输入”。
- 对过期任务返回可识别的终止原因，不把过期结果当成功；此前有效的旧作品继续可见。
- 单图已经验证的观察结果可按第三章规则保留；这不等于允许过期 workflow 发布正式叙事。

### 2.5 本模块验收

| 编号 | 场景 | 正确结果 |
| --- | --- | --- |
| S01 | 旧保存等待正文期间，新叙事完成发布 | 旧保存 409，正文与覆盖层不被旧内容改写 |
| S02 | 两个标签页基于同一编辑修订保存同一字段 | 后到的旧修订被识别为冲突，草稿保留 |
| S03 | 点击保存后继续尝试输入 | 只读状态明确，或新草稿被完整保留，不能静默丢字 |
| S04 | 有草稿时点击下一步，保存失败/冲突 | 不跳转，保留文字，允许处理后重试 |
| S05 | 改语气生成被占用拒绝或中途失败 | 正式语气、编辑、叙事和版本不变 |
| S06 | 快速重复提交同一 request_id | 只有一个业务任务，无重复意图副作用 |
| S07 | 上传处理期间另一个任务启动 | 最终提交拒绝，无新增照片或本次文件残留 |
| S08 | 多上传同时逼近素材上限 | 最终数量不超限，不依赖前端串行 |
| S09 | agent 等待期间输入修订或租约失效 | 过期结果不发布，不覆盖当前作品 |

## 3. 模块二：断点恢复与有效缓存复用

对应用户要求第 3 项。目标是少重复调用，同时保证复用的确是当前有效结果。

### 3.1 先解决已知预算死路

现有视觉缓存与 workflow 绑定，重试新建 workflow 后无法复用上一轮成功分析；素材分析又重新遍历全部照片。已有持久影展预算，因此重复调用可能先耗尽额度。

**必须覆盖的复现场景：**

30 张照片，前 29 张成功，第 30 次请求失败。重试应复用 29 项已验证结果，仅补失败照片，而不是从第一张重新请求。若补齐一次成功，视觉阶段累计为 31 次实际尝试；后续筛选、主题和叙事请求另计，不能把它们漏出账本。

### 3.2 复用范围与有效性

首要范围限定为**同一影展内的单图视觉事实**，允许跨 workflow 及服务重启复用。不要为本轮建立跨用户、跨影展的全局照片内容库。

有效性至少包含：

| 因素 | 要求 |
| --- | --- |
| 所属范围 | 同一影展；当前照片仍存在，且有使用这些 AI 结果的合法上下文 |
| 图片内容 | 使用真实分析副本的内容摘要，不仅靠文件名或照片 ID |
| 服务与模型 | 服务配置标识、服务地址身份、实际模型；不同配置不得误命中 |
| 输入 | 实际发送的技术指标、上下文等影响输出的输入摘要 |
| 版本 | 提示词版本、schema 版本、预处理版本 |
| 生成选项 | 对输出有影响的有效参数；避免遗漏导致旧结果冒充新结果 |
| 结果状态 | 之前成功且通过完整校验，内容未损坏 |

配置标识不得包含明文 Key，也不要在客户端或日志暴露密钥相关摘要。缓存键不要包含每次都会变化的 workflow/run ID；审计记录仍要保留本次 workflow 与原始调用的关联。

素材全局修订变化不应一律使未变图片的原始视觉事实失效。例如只增加一张照片，可复用其余照片的独立事实，再重算受整个素材集合影响的去重、筛选或主题。

**复用前也需检查当前权限与状态。** 撤销外发授权后不能借缓存分支触发后续模型调用；是否允许查看已有本地作品沿用当前产品规则，不因撤销授权销毁旧作品。

### 3.3 恢复策略

1. 按照片识别“可复用、需补分析、失败、已删除或不可用”，从有效状态继续。
2. 缓存命中仍通过当前 schema 和引用上下文校验；损坏或不兼容记录不得被当成成功。
3. 缓存失效若需要新请求，仍走当前授权、预算、并发和计账路径，不静默绕过限制。
4. 在进程重启后复用已持久化成功结果；对发送后未确认结果的请求标记为不确定，不凭空补成成功。
5. 相同图片的并发请求继续复用现有同进程合并能力；不同输入不能被合并。
6. 本轮不要求把所有文本阶段都做成复杂的跨 workflow 缓存。先保证单图恢复正确，再用现有 rerun 规则精确执行受影响的下游。

### 3.4 操作与阶段依赖

| 用户操作 | 原则 |
| --- | --- |
| 修改影展标题/副标题文字 | 本地编辑及必要布局失效，不重新识图 |
| 只调整语气并请求重新生成 | 重跑必要的叙事及下游，不重新识图或重新选片 |
| 调整章节顺序 | 按既有结构依赖更新布局与 QA，不重新识图 |
| 调整保留/移除决定 | 按确认门和 rerun 规则更新下游，未变图片的视觉事实仍可复用 |
| 新增/替换/删除照片 | 只重算受影响的单图事实及集合级下游；确认状态相应失效 |
| 切换视觉模型、提示词或预处理 | 对应视觉事实失效，明确将产生新请求 |
| 切换文本模型 | 重算受影响文本阶段，不能无理由让未变的视觉结果一起失效 |

以项目现有 rerun 矩阵为基础处理，不随意自动越过筛选确认和主题选择。阶段完成必须对应本次任务和当前修订，不能因为数据库里有旧结果就自动前进。

### 3.5 不通过重试重置预算

- 同一影展的持久任务预算继续累计；重试、新 workflow、服务重启和模式切换都不自动扩额。
- 已实际发出的失败、超时及输出不合法请求仍计实际尝试；缓存复用不新增外发计数。
- 已发送但结果未知时按保守原则处理，不承诺“未成功就不计费”。
- 已经用完的预算不因为本轮修复自动返还。界面说明剩余工作和限制，不诱导无限重试或新建影展绕过限制。
- 若确实无法在既有额度内完成，保留已完成结果并给出明确原因；本轮不新增额度重置或自动扩额入口。

### 3.6 页面反馈

在现有分析进度区域增加真实可核对的反馈，例如：

> 已完成 29/30 张，其中复用 29 张；本次待分析 1 张。

成功、复用和失败状态来自服务端，不用定时器模拟进度；页面刷新后仍能恢复展示。

### 3.7 本模块验收

- [ ] 29 成功、1 失败场景，重试仅补失败项，已成功事实不重复外发。
- [ ] 服务重启后仍能识别并复用持久化的有效事实。
- [ ] 单张替换只使受影响事实失效；集合级结果按依赖重算。
- [ ] 改标题、语气、章节顺序不会重新分析全部图片。
- [ ] 模型、提示词、schema、预处理或有效输入变化时正确失效。
- [ ] 损坏缓存、删除照片和授权撤销不会造成假完成或越权外发。
- [ ] 复用记录保留原始来源和本次关联；调用账本不被改写为“新调用成功”。

## 4. 模块三：共享并发限制与消耗展示

对应用户要求第 4 项。先让限制真实生效，再让用户看懂。

### 4.1 让 AI_MAX_CONCURRENCY 实际约束外发

**现状入口：** `src/lib/ai/config.ts`、`src/lib/ai/client.ts`。

此前隔离验证配置为 1 时，3 个不同请求的实际峰值仍达到 3。不能只读取配置或限制某个页面按钮。

**必须实现：**

1. 在共享请求层建立有界队列/信号量，约束当前本地单服务进程中同一服务配置的实际在途模型请求。
2. 不同 AiClient 实例、不同影展及各业务 agent 不能通过各自新建 limiter 绕过上限；连接探测也纳入明确一致的外发并发规则。
3. 并发 1 时最多一个实际请求；并发 2 时最多两个。不要以 workflow 数或任务数代替实际 HTTP 请求数。
4. 每个实际尝试，包括重试、格式修复，都应经过 limiter。
5. 成功、异常、超时、取消均在可靠的 finally 路径释放名额；排队本身可取消，有最大等待或明确的排队上限，不能无限积压。
6. 排队结束、真正发送前重新核对授权、任务状态/修订、当前有效配置和预算；排队时撤销授权的请求不得继续外发。
7. 不要求跨进程或分布式锁；验收结果明确限定单服务进程。不要对本轮未实现的部署方式承诺全局限制。

### 4.2 推荐请求顺序

按以下语义组织，具体函数可复用当前代码：

1. 检查输入及当前上下文；尝试使用已验证缓存或合并同请求。
2. 必须新请求时进入共享队列。
3. 获得名额后再次检查缓存及最新授权、输入修订、配置和预算。
4. 原子预留预算并建立调用记录，在即将外发时记录 sent。
5. 发送、读取有界响应、解析校验、更新调用记录；发布前还要检查任务状态。
6. 释放并发名额；确定没有外发的预留才可按现有机制释放。

不要在排队开始就将请求计为“已经发送”。不能保证到底有没有发出的故障，保留“不确定”语义并保守计账，不伪造精确一次外发保证。

### 4.3 调用次数与预算口径

至少区分三类：

- **本次运行：** 本次 workflow 的实际尝试、新完成、复用和失败。
- **当前影展：** 持久业务任务预算的已用/上限/剩余，不随重试清零。
- **全局日预算及连接探测：** 继续按当前机制计账；探测计入其全局和小时额度，不能被误说成包含在影展业务额里。

应明确：

| 行为 | 新增外发尝试 | 说明 |
| --- | --- | --- |
| 本地缓存复用 | 0 | 展示复用数及原始来源 |
| 等待队列、状态轮询、浏览、播放、导出 | 0 | 不应触发模型调用 |
| 发送失败后再次请求 | 每次发送均计 | 不因最终失败清除历史次数 |
| 模型响应格式修复 | 若重新调用则计 | 不是“免费本地修复” |
| 服务商侧提示词缓存命中 | 仍计一次请求 | 不等同于本地结果缓存；金额以 usage/费率为准 |
| 预算预留但确定尚未发送 | 不计已发送 | 账本可保留 released 状态 |

界面展示的调用数、账本状态和预算需能对上，不靠前端自行累加。次数上限不是金额上限，也不是“还能分析多少张照片”的精确保证。

### 4.4 页面上应该看见什么

复用现有进度和状态区域，分成“简洁默认 + 可展开详情”，不新增复杂后台。

**默认可见：**

- 当前阶段及状态：排队、分析、筛选、主题、叙事、完成或失败。
- 素材完成数/总数、复用数、失败数；确有在途请求时显示正在处理。
- 本次实际请求数，当前影展剩余业务调用额度。
- 错误后的下一步：重试失败项、等待后再试、检查配置或额度不足。

**展开详情：**

- 业务累计额度、全局日额度、最近连接测试的独立消耗及时间。
- 模型名称、阶段耗时、已知 token usage 和脱敏后的错误分类。
- 若支持费用估算，标注估算依据、币种、费率生效日期和范围。

**示例文案：**

> 素材分析：29/30 张已完成，复用 29 张，失败 1 张。
> 本次已发送 1 次请求；当前影展业务额度剩余 9 次。
> 下一步将仅重试失败照片；之后的策展阶段也会消耗调用额度。

示例数字只说明表现形式，实施时必须使用真实服务端数据。

### 4.5 费用估算的边界

本轮必须完成调用次数与预算展示；费用不能靠猜。

- 费率未配置：显示“未配置价格，暂不估算费用”。
- usage 缺失或不能可靠拆分计费：显示“消耗未知”或“估算不完整”，不能显示 0 元。
- 仅当 usage 与相应模型费率都可核对时计算；使用可配置费率，不在代码和文案写死 DeepSeek 当前价格。
- 若存在缓存输入等不同计费项目，按有文档依据的分类计算；不能误把 total_tokens 与分项再次相加，或重复计算思考 token。
- 部分请求没有 usage 时，不将已知小计标成“全部总费用”。
- 缓存复用可标注“本次没有新增模型请求”，不能把历史已付出的成本抹成零。
- 界面明确“估算，以服务商账单为准”；不承诺预算次数能防止所有金额超支。

本轮不需要实时抓取价格、接入支付或新增账单系统。费率不完整时诚实显示无法估算，即为正确行为。

### 4.6 本模块验收

- [ ] 跨 AiClient、跨影展并行时，并发配置 1/2 的实际 transport 峰值分别不超过 1/2。
- [ ] 连接探测和重试没有绕过并发限制。
- [ ] 超时、网络失败及取消后名额可释放，后续请求不被永久阻塞。
- [ ] 排队后授权撤销、任务过期或预算不足，请求不外发。
- [ ] 队列满/超时有反馈，不占用虚假已发送额度。
- [ ] 页面刷新后计数一致；本地缓存、轮询和导出不增加请求数。
- [ ] 连接探测、业务预算和全局日预算的展示没有混算。
- [ ] usage 或价格未知时不显示 0 元、不展示虚假总费用。

## 5. 模块四：模型输出校验与失败处理

对应用户要求第 5 项。目标是“有效结果才发布”，不承诺仅靠规则完全消除幻觉。

### 5.1 沿用统一请求层，分层校验

**检查并扩展的位置：**

- `src/lib/ai/client.ts`、`errors.ts`、`schemas.ts`、`prompts.ts`
- `src/lib/adapters/aiVisionAdapter.ts`、`aiTextAdapter.ts`
- `aiCurationAdapter.ts`、`aiMotifAdapter.ts`、`aiNarrativeAdapter.ts`
- `src/lib/agents/credibility.ts` 和既有 QA/合并发布逻辑

| 层级 | 检查重点 | 失败后行为 |
| --- | --- | --- |
| 传输/响应封套 | HTTP 状态、响应体上限、choices/message/content、明确的截断标记 | 分类错误，不将响应交给正式发布 |
| 解析 | 非空最终输出、合法 JSON | 空白/非法 JSON 视为失败，不转空对象充数 |
| 结构 | 当前 schema 的字段、类型、枚举、长度和数量 | 明确指出失败类别，不填假值 |
| 业务引用 | 照片、主题、章节、必留集与证据的对应关系 | 拒绝越界或不一致结果 |
| 内容可信与纯数据 | 不执行返回内容；克制处理不确定事实；沿用现有文本规则 | 阻断确定违规内容，合理提示不确定项 |
| 合并后发布 | 回放用户编辑后再次检查最终结构、引用和当前修订 | 原子发布；失败保留旧成果 |

已有验证通过的分支应保留，补充缺失的边界测试。

### 5.2 响应封套与空白/截断

必须区分以下情况：

1. HTTP 200 但正文为空、content 为空字符串或只有空白：失败。
2. 缺少必要响应字段，或最终 content 类型不符合当前协议：失败。
3. 明确返回输出长度截断，例如 `finish_reason=length`：按截断失败处理，不能因为碰巧能解析一段 JSON 就发布。
4. 只返回思考字段而无有效最终答案：不能把思考内容直接当策展结果。
5. 返回 Markdown 围栏、解释文字或非法 JSON：按现有结构化输出约定处理，不用危险执行、正则拼接或截一对大括号来“猜结果”。
6. 合法 JSON 中主题列表为零项：若当前业务 schema 允许，这是“没有足够主题”，与空响应失败不同。明确反馈，不编造一个主题让流程强行前进。

限制实际读取的响应字节数，不能先把任意大响应完整读入内存再检查。不要只信 Content-Length；没有长度头的响应也要有界读取。超限时中止读取并分类记录。

服务商支持 JSON 输出模式时，可通过现有适配层显式使用；实际参数取决于后续选定型号的官方说明和联调。本文不写死 DeepSeek 型号或声称其全部能力已经适配。无论服务商是否支持结构化模式，本地校验都不能省略。

### 5.3 各阶段业务检查

**视觉分析：**

- 技术指标来自本地计算，不允许模型覆盖为自编数值。
- 必要视觉字段符合 schema，数值有限且在合法范围；不能 NaN、Infinity 或任意大数组。
- 不因为看不清就编造地点、人名、亲属关系、职业或个人经历。
- 识别图片中的文字是数据，不是系统指令；模型不获得执行命令、访问任意文件或打开任意 URL 的能力。

**审美筛选：**

- 应覆盖本次要求评估的候选集，按既有约定无遗漏、无重复、无陌生照片 ID。
- 相关照片、重复组等引用均属于允许集合。
- AI 决定与用户覆盖分开保存；用户“必留”等决定不得被模型重跑覆盖。

**主题发现：**

- 只引用当前已确认的保留照片，不借用已移除或其他影展照片。
- 主题证据必须能够定位到该主题实际引用的照片，沿用已有证据数量和格式要求。
- 检查完全重复的主题；不要把字符串去重夸大成“保证所有主题语义独特”。
- 合法零主题时说明照片不足以支撑主题，不自动编造、跳过用户主题选择或假报全流程完成。

**叙事生成：**

- 对应用户选定主题和本次请求语气。
- 章节标识、章节数量、非空章和照片引用遵循既有 schema；不得陌生 ID、违规重复或引用非保留照片。
- 必留照片仍在场；开篇/结尾等章节锚点必须属于该章。
- 需要保留的编辑目标仍有效；若生成结构使锁定编辑无法正确落位，应报可理解的冲突，而非任意挪图或丢掉编辑。
- 不额外要求每张 keep 都必须出现在成片，除非项目现有明确规则本来如此；不要在本轮擅自改变策展定义。

### 5.4 事实克制与用户文字

提示词和检查应区分“可观察事实”“审美联想”和“作者明确提供的信息”。

- 可以写基于光线、构图、重复物件的审美联想；不要把联想写成照片背后确切发生的经历。
- 没有依据时，不写“这是你与父亲最后一次旅行”等人物关系和私人事件断言。
- 不确定的推断可以省略或用克制措辞，不强行填满所有信息。
- 现有规则只能降低风险，不能证明所有文字绝对真实或完全防提示注入。验收报告必须保留这个边界。
- 不用过宽的关键词规则误删作者自己明确写下的真实信息；继续尊重用户编辑和锁定层。

本轮不新增另一组付费“审判模型”来给所有输出二次评分；先完善确定性检查与已有可信度规则。

### 5.5 失败、格式修复与重试

沿用当前预算和重试配置，并明确额外请求的上限。不得由多个层级各自修复一次，形成隐藏的多倍调用。

| 错误类别 | 行为要求 |
| --- | --- |
| Key 无效、权限不足、余额/硬额度不足 | 停止并提示检查，不盲目重试 |
| 预算不足、授权撤销、输入过期 | 本地阻断，不继续调用模型 |
| 429/可恢复服务故障 | 仅按配置进行有上限重试，遵守合理的 Retry-After；每次外发计数 |
| 超时 | 正确标为 timeout，不承诺服务商未处理；默认不因结果未知自动反复发送 |
| 用户取消/任务失效 | 与超时和网络错误区分；停止后续调用和发布 |
| 空白、非法 JSON、截断或 schema 错误 | 明确失败；若已启用格式修复，必须受下述统一约束 |
| 照片越界、必留遗漏、证据无效 | 不发布，不用随机删图/补 ID/改内容强行过检 |

**格式修复统一约束：**

- 默认不为了“更容易成功”额外开启此前关闭的自动修复；遵循显式配置。
- 若保留自动格式修复能力，每次逻辑请求至多一次，且与网络重试共享清晰、可计算的总尝试上限。
- 修复也是一次新外发，照常经过授权、任务状态、预算、并发和调用记录。
- 修复仍完整校验；失败保留旧成果，不无限循环。
- 不把业务事实错误伪装成格式问题，反复调用直到碰巧过检。

**特别修复：** 当前使用 `AbortSignal.timeout()`，错误识别不能仅接受 `AbortError`；应根据本次超时信号和实际原因识别 `TimeoutError`，同时不把其他取消一律记成超时。

### 5.6 正式成果与中间结果分开

- 单图有效分析可逐项持久化，以便断点恢复。某一张失败时，不必删除其他成功事实。
- 但素材批次没有全部满足当前阶段完成条件，就不能假报整批完成或自动跳到下一阶段。
- 筛选、主题、叙事各阶段只有完整输出、用户编辑合并和必要校验通过后，才在对应边界原子提交。
- 最终叙事与其版本、意图、来源元数据应一致；失败时不能留下“新版本号 + 旧/半份内容”。
- 模型失败时保留当前可用影展和编辑内容，并显示失败发生在哪一阶段、已完成什么、可重试什么。
- 不在真实 AI 失败时悄悄回退为 Demo 文案，再标成 AI 成功。

### 5.7 错误反馈与脱敏

用户应看到类似：“叙事生成未完成：模型输出被截断。原有影展和编辑内容已保留，可稍后重试。”

技术详情记录阶段、调用 ID、模型标识、错误类别和受限长度的脱敏摘要；不回显服务商完整错误体、原始请求、Key、图片数据或本地路径。不要让用户只看到无法行动的“发生错误”。

### 5.8 本模块验收

用 Mock 固定响应测试，至少包括：

- [ ] 空响应、空白 content、缺字段、错误 content 类型、只返回思考内容。
- [ ] 非法 JSON、schema 不符、明确长度截断、响应超过字节上限。
- [ ] 完全合法输出正常通过；合法零主题正确提示，不被误判成网络失败。
- [ ] 陌生/重复照片 ID、引用移除照片、必留遗漏、主题证据不对应、章节锚点越界。
- [ ] 回放用户锁定编辑后结构不合法，拒绝发布且旧叙事与编辑不变。
- [ ] 提示注入式图片文字或模型返回 HTML/脚本，仅作为数据处理，不能执行。
- [ ] 真实超时信号归为 timeout；取消、网络、限流和预算错误分别处理。
- [ ] 格式修复/重试的实际请求数有总上限，每次尝试记账，不会隐式倍增。
- [ ] 每种失败下，旧内容、版本、语气和编辑一致；单图成功事实可供合法恢复。
